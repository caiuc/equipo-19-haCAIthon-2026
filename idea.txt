1. Idea de la aplicación

Estamos desarrollando una plataforma web educativa donde existen dos tipos de usuarios:

Profesor
Estudiante

Los profesores crean salas/clases y los estudiantes pueden unirse mediante un código.

Una vez que un estudiante entra a una sala, la sala queda guardada permanentemente en su cuenta mediante la relación room_members.

Dentro de una sala, el profesor podrá crear actividades y seleccionar:

Materia.
Tipo de ejercicio.
Dificultad.
Cantidad.
Modalidad:
En vivo.
Tarea.
Práctica.

Los estudiantes realizan los ejercicios y el profesor puede ver resultados y estadísticas.

La idea para el MVP es:

Profesor crea sala
        ↓
Estudiante entra mediante código
        ↓
Profesor crea/inicia actividad
        ↓
Estudiantes reciben ejercicios
        ↓
Estudiantes responden
        ↓
API corrige respuestas
        ↓
Profesor ve resultados

5. Tabla profiles
create table public.profiles (
  id uuid primary key
    references auth.users(id) on delete cascade,


  name text not null,


  role text not null
    check (role in ('teacher', 'student')),


  created_at timestamptz not null default now()
);

Sirve para guardar datos adicionales del usuario.

6. Tabla rooms
create table public.rooms (
  id uuid primary key default gen_random_uuid(),


  code text not null unique
    default upper(
      substr(
        replace(gen_random_uuid()::text, '-', ''),
        1,
        6
      )
    ),


  name text not null,


  teacher_id uuid not null
    references auth.users(id) on delete cascade,


  status text not null default 'waiting'
    check (
      status in ('waiting', 'live', 'closed', 'active')
    ),


  created_at timestamptz not null default now()
);

Una sala tiene:

id
code
name
teacher_id
status
created_at

Ejemplo:

name: Matemáticas I
code: 11
teacher_id: UUID profesor
status: active
7. Tabla room_members

Conecta estudiantes con salas.

create table public.room_members (
  id uuid primary key default gen_random_uuid(),


  room_id uuid not null
    references public.rooms(id) on delete cascade,


  user_id uuid not null
    references auth.users(id) on delete cascade,


  joined_at timestamptz not null default now(),


  unique(room_id, user_id)
);

Esto permite que las clases queden guardadas permanentemente en la cuenta.

Por ejemplo:

Camila
    │
    ├── Matemáticas
    ├── Física
    └── Programación

No necesitamos guardar el nombre en room_members, porque podemos obtenerlo desde profiles.

12. RLS

Tenemos Row Level Security habilitado en las tablas.

alter table public.profiles enable row level security;
alter table public.rooms enable row level security;
alter table public.room_members enable row level security;
alter table public.activities enable row level security;
alter table public.exercises enable row level security;
alter table public.exercise_keys enable row level security;
alter table public.answers enable row level security;

Durante las pruebas descubrimos que:

supabase.table("rooms").select("*").execute()

devolvía:

[]

aunque las salas existían.

Esto era porque el cliente estaba consultando sin una sesión autenticada y RLS bloqueaba el resultado.

Cuando hicimos login primero:

supabase.auth.sign_in_with_password(...)

las rooms aparecieron correctamente.

13. Decisión para el backend

Para simplificar la hackathon, conviene manejar dos clientes de Supabase.

Cliente normal
→ Auth

20. routers/auth.py

Login:

from fastapi import APIRouter, HTTPException


from schemas.auth import LoginRequest
from database import supabase




router = APIRouter(
    prefix="/auth",
    tags=["Auth"]
)




@router.post("/login")
def login(data: LoginRequest):


    try:
        response = supabase.auth.sign_in_with_password({
            "email": data.email,
            "password": data.password
        })


        return {
            "access_token": response.session.access_token,
            "refresh_token": response.session.refresh_token,


            "user": {
                "id": response.user.id,
                "email": response.user.email
            }
        }


    except Exception:
        raise HTTPException(
            status_code=401,
            detail="Email o contraseña incorrectos"
        )

El frontend manda:

{
  "email": "profe@test.cl",
  "password": "password123"
}

y recibe:

{
  "access_token": "eyJ...",
  "refresh_token": "...",
  "user": {
    "id": "...",
    "email": "profe@test.cl"
  }
}

22. dependencies/auth.py

Esta función valida el token y obtiene al usuario.

from fastapi import Depends, HTTPException


from fastapi.security import (
    HTTPBearer,
    HTTPAuthorizationCredentials
)


from database import supabase




security = HTTPBearer()




def get_current_user(
    credentials: HTTPAuthorizationCredentials = Depends(security)
):


    token = credentials.credentials


    try:


        response = supabase.auth.get_user(token)


        if response.user is None:
            raise HTTPException(
                status_code=401,
                detail="Token inválido"
            )


        return response.user


    except Exception:


        raise HTTPException(
            status_code=401,
            detail="No autorizado"
        )

Así cualquier router puede hacer:

current_user = Depends(get_current_user)

y después usar:

current_user.id

24. routers/rooms.py

Como queremos que /rooms muestre todas las salas para un usuario autenticado:

from fastapi import APIRouter, Depends


from dependencies.auth import get_current_user
from database_secret import admin_supabase




router = APIRouter(
    prefix="/rooms",
    tags=["Rooms"]
)




@router.get("/")
def get_rooms(
    current_user = Depends(get_current_user)
):


    response = (
        admin_supabase
        .table("rooms")
        .select("*")
        .execute()
    )


    return response.data

La llamada requiere:

Authorization: Bearer TOKEN

Por eso si escribes directamente:

http://127.0.0.1:8000/rooms/

en el navegador aparece:

Not authenticated

Eso es correcto.

25. Crear una sala

En rooms.py:

from schemas.room import RoomCreate




@router.post("/")
def create_room(
    room: RoomCreate,
    current_user = Depends(get_current_user)
):


    response = (
        admin_supabase
        .table("rooms")
        .insert({
            "name": room.name,
            "teacher_id": current_user.id
        })
        .execute()
    )


    return response.data

El frontend solamente manda:

{
    "name": "Matemáticas I"
}

FastAPI obtiene automáticamente:

current_user.id

No hacemos:

{
    "teacher_id": "..."
}

porque un usuario podría intentar crear una sala a nombre de otro.

38. Borrar usuarios

Eliminar un usuario completamente:

admin_supabase.auth.admin.delete_user(
    "UUID_DEL_USUARIO"
)

Como tenemos on delete cascade, puede eliminar también datos relacionados.

Por eso hay que tener cuidado, especialmente con profesores que tengan salas.
